# 实验记录：这套协议是怎么被验证的

> 目的不是证明"我说得对"，而是先假设它没用，再设计能推翻它的实验。

## 通用设计

- 每次都跑**两个智能体**：A 组只给需求原文，B 组在需求前加四关协议
- 两者模型相同、工具相同、字数限制相同（300 字）、都要求"只给方案不实现"
- 评分由人按固定口径判定，不看措辞看内容

## 实验 1：最初的对照（4 次运行）

| 项目 | 说明 |
|---|---|
| 任务 | ①安卓上跑 DSH + AI 操作手机 ②B 站视频下载器 |
| 结果 | 对照 0/2 提到已有方案；实验 1/2 |
| 发现 | 协议里的"写验收句/判档位"稳定生效；"召回"只成功一半 |

## 实验 2-3：重跑（4 次运行）

| 项目 | 说明 |
|---|---|
| 变更 | 给每个智能体加"先 dir 再等 20 秒"，保证运行可见 |
| 结果 | 对照 0/2；实验 2/2 点名已有方案 |
| 发现 | 实验组还多做了"核实项目是否还活着"——发现某个被推荐的项目档案已归档 |

## 实验 4：用预训练之后的新项目排除"靠记忆"（8 次运行）

| 项目 | 说明 |
|---|---|
| 任务 | 4 个 DSH 插件需求，答案取自 **2026-11 创建、27–40 星**的冷门项目 |
| 为什么 | 前面的任务（yt-dlp、DSH-Android）都在模型知识里，分不清"想起"还是"搜到" |
| 结果 | 对照 **0/4** 点名方案；实验 **4/4** 点名（精确命中 1/4） |
| 发现 | 协议的作用不是"命中特定仓库"，而是"不再从零造"；对照组 4 个全部自己设计架构 |

## 实验 5：2×2 交叉，验证"停顿"是不是原因（16 次运行）

假设：实验 2-3 变好，是因为"先做一件耗时的事"让模型更认真。

| 组 | 前置动作 | 协议 | 点名任何真实项目 |
|---|---|---|---|
| A | ❌ | ❌ | 0 / 4 |
| B | ❌ | ✅ | 4 / 4 |
| C | ✅ | ✅ | 4 / 4 |
| D | ✅ | ❌ | 0 / 4 |

**结论：假设被推翻。** 有协议 8/8 点名，无协议 0/8；前置动作在有、无协议两种情况下都没改变结果。

因此"停顿"没有写进 skill。

## 实验暴露的三个具体缺陷

1. **0 结果不等于没有**：一个 agent 只搜"便签墙"得到 0，就写"未发现现成插件"，而生态里确实有 `notewall`。→ 已写入 rule ②b：换三组说法重搜。
2. **推荐了已归档项目**：实验 1 的实验组推荐了某个后来发现已归档的库。→ 已要求核实"最近活跃"。
3. **把本地半成品当成答案**：对照组把工作区里一个自研原型当成"可直接复用"，而它和需求不是同一条技术路线。→ 已要求区分"名字沾边"和"真能解决"。

## 测量口径

- **L1 点名任何真实存在的项目**：库、产品、插件都算
- **L2 点名真正解决同一需求的东西**：纯库不算
- 项目状态以 GitHub API 的 star/更新时间与仓库页为准
