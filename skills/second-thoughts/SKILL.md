# 三思而后行 · 开工前协议

> 目标不是"显得认真"，是**不漏**、**不糊弄**。
> 两道关：**召回**（别重造已有的东西）和**达标**（别交缩水货）。

---

## 第 0 关：把需求写成能验收的话

用户说得含糊是常态，**含糊不等于可以随便做**。你要替他把话说清楚，而不是把标准降下来。

### 模板（EARS 句式）

```
当 <触发条件> 时，系统应该 <可观察的行为> [，误差/时限为 <数值>]
```

**例**：用户说"做个下载器"

| 用户原话 | 你要写成的验收句 |
|---|---|
| 能下载 | 当用户粘贴一个 http/https 链接时，程序应该在 3 秒内开始下载 |
| 别断了 | 当网络中断后恢复时，程序应该从断点续传，不重新下载已完成部分 |
| 能看进度 | 下载过程中，界面应该每 500ms 更新一次百分比和速度 |
| 别乱存 | 下载完成后，文件应该保存在用户指定目录，重名时自动加序号 |

### 三条硬规则

1. **需求含糊时向上收口**：写出你理解的验收句，标明"我替你定了 X，不同意就说"，**不许**默默按最低标准做。
2. **缺的信息变成待办**：列出来（数据从哪来 / 部署到哪 / 谁维护），不要跳过。
3. **该拒绝时拒绝**：做不到就说做不到，给差距和替代方案，**不许交一个缩水版冒充完成**。

### 同时问自己：这是什么事？

| 性质 | 标准档位 |
|---|---|
| 一次性脚本 | 能跑通 + 有注释 |
| 自己长期用的工具 | 有错误处理 + 能重装 + 有说明 |
| 给别人用的产品 | 并发 + 持久化 + 日志 + 测试 + 部署 |
| 工业系统 | 上面全部 + 容量规划 + 故障恢复 + 监控告警 |

**档位由"这事要拿去干什么"决定，不由用户说话的专业程度决定。**

## 第 1 关：自己找源，并且验证源

**不要用固定源清单。** 固定清单在出现新平台的那天就失效了。

### ① 自拟候选源

先问：这类东西按常理会出现在哪？按领域、语言、新旧、官方/野生分别列。起步参考（不是边界）：

| 层 | 起步源 |
|---|---|
| 仓库 | GitHub（中英各搜一遍，按更新时间排序）、Gitee、GitLab |
| 代码 | grep.app 一类跨仓库代码搜索，按函数名 / 协议名 / 架构词 |
| 包 | npm、PyPI、Maven、Crates、应用商店 |
| 本生态 | DSH 插件市场、agent skill 市场、awesome-list |
| 社区 | Discussions、issue、HN、Reddit、V2EX、知乎、博客、B站、公众号 |
| 新平台 | **你自己补**：最近半年出现的、这个领域专用的 |

### ② 探针验证（关键，别省）

每个候选源跑一次**已知答案**的查询：

```
拿一个你确定存在的项目名去搜该源
  搜到了 → 该源可用，记下来
  搜不到 → 该源不可靠或需登录，标出来，换一个
```

**只报告你验证过能用的源。** 没验证就写"我搜过了"，等于没搜。

### ③ 记忆

把验证通过的源记进工作区（如 `sources.json`），下次直接用；发现新平台就追加。
**本次新增了哪些源、哪些源失效了，要告诉用户。**

## 第 2 关：召回，直到没有新东西

### ① 按能力搜，不按名字搜

把需求拆成能力项（并发 / 持久化 / 离线 / 多端同步 / 权限模型…），逐项检索。
同类项目命名千奇百怪：`dsh-Go` 和 `deepseek-harness-android` 是一回事，词面零重叠。

### ② 种子扩展（比换关键词有效得多）

找到第一个同类之后，**不要换关键词，而是顺着它爬**：

- 它的 `dependents`（谁依赖它）
- README 里的 `alternatives` / `对比` / `inspired by` 段
- issue 里被提到的竞品名
- 它的 star 列表 / fork 去向

### ③ 反向检索

搜「X 太难用」「有没有替代品」「为什么没人做」——评论区通常直接点名项目。

### ④ 停止条件

**连续 2 轮没有新候选**就停。不是"查完了所有源"（无边界语料上不存在），也不是"感觉够了"。

### ⑤ 对照表

| 候选 | 链接 | 热度 | 最近活跃 | 命中哪些能力项 | 重合度 |
|---|---|---|---|---|---|
| owner/repo | URL | ★/下载 | 日期 | 能力 1、3 | 60% |

## 第 3 关：判定与声明

### 判定漏斗

```
能直接用      → 用，并说明为什么够用
差一点        → 提 issue / PR 贡献
确实空白      → 自建，附检索日志
```

### 覆盖声明（强制）

必须写清楚：

```
已查（且验证可用）：GitHub / grep.app / npm / DSH 市场 / DDG
已查但不可用：SearXNG（429）
未覆盖：QQ 群、微信群、公众号、B站 —— 这些基本无法检索
结论：在可检索范围内未找到；不等于不存在
```

**禁止把"我没找到"写成"不存在"。**

## 第 4 关：交付对账

交付前逐条对照第 0 关的验收句：

```
1. 3 秒内开始下载      —— 达成（tests/start_latency.log）
2. 断点续传            —— 达成（tests/resume.log）
3. 每 500ms 更新进度   —— 部分达成（1s 刷新，原因：UI 线程限制）
4. 重名自动加序号      —— 未达成（未实现），补法见 TODO
```

**未达成必须显式写出来。** 不许用"不影响使用"带过，也不许把 demo 说成完成。

## 反模式

- ❌ 需求含糊就做简单点
- ❌ 用户说得专业就特别认真，说得朴素就应付
- ❌ 用一个固定的源清单，然后声称"搜不到"
- ❌ 只按产品名搜，不按能力搜
- ❌ 找到第一个就停，不做种子扩展
- ❌ 交了半成品，用"后续可以优化"包装成完成
- ❌ 把"证据齐全"当成"做对了"——引用的每句话都对，结论仍然可以是错的

**本协议不依赖它们，也不重复它们。**
